# Signal CLI Agent

A YAML-driven automation framework that connects to [`signal-cli`](https://github.com/AsamK/signal-cli) via DBus and maps trusted Signal messages to controlled actions on your host system.

This project is intentionally **extensible**:

- Add production rules without modifying the agent
- Ship example templates in `templates/` and render them into `rules.d/`
- Keep your own rules in `rules.d/` — they are never removed by `make clean` / `make uninstall`
- Use helper scripts for API integrations (Home Assistant, monitoring, etc.)
- Choose reply formats (`full`, `output`, `bare`)
- Support manual runs or persistent systemd user services

---

## Quick Start (one-command)

From the repo root (recommended):

```sh
make quickstart
```

This runs `configure.py` (renders templates), installs user units, and starts the services.

Then check status & logs:

```sh
make status
make logs
```

## Repo Structure

Project uses a templates → generated model. `configure.py` renders shipped templates into the generated locations.

```
.
├── Makefile
├── configure.py
├── signal-agent.py
├── rules.yaml.in                 # template (rendered -> rules.yaml)
├── rules.yaml                    # generated by configure.py
├── rules.d/                      # PRODUCTION rules (user-editable)
│   ├── custody-week.yaml         # example of a user rule (user-managed)
│   └── example-rules.yaml        # generated from templates/rules/example-rules.yaml.in
├── systemd/                      # generated service units (rendered)
│   ├── signal-agent.service
│   └── signal-cli-dbus.service
└── templates/                     # shipped templates (source-of-truth)
    ├── rules/
    │   └── example-rules.yaml.in
    └── systemd/
        ├── signal-agent.service.in
        └── signal-cli-dbus.service.in
```

**Important:** `templates/` contains the files *we ship*. `configure.py` renders those into `systemd/` and into `rules.d/` **only for shipped templates** (for example `example-rules.yaml`). Any other files you add to `rules.d/` are considered user-owned and **will not** be touched or deleted by `configure.py`, `make clean`, or `make uninstall`.

## Rules & Templates (how it works)

- `rules.yaml.in` (template) → `rules.yaml` (rendered). `rules.yaml` contains `globals:` and `rules_dir:` and optionally inline `rules:`.
- `templates/systemd/*.service.in` → `systemd/*.service` (rendered systemd unit files).
- `templates/rules/*.yaml.in` → `rules.d/*.yaml` (rendered example rules). These are the *only* the shipped example rules we generate.
- `rules.d/` is the **production** rules directory. Add your own rule files there (e.g., `custody-week.yaml`) — they will be loaded by the agent and **never** removed by the project tools.

Agent loads:
1. `rules.yaml` (root config)
2. Every `.yaml` / `.yml` in `rules.d/` (merged in load order)

Supported rule file formats:  
- `rules:` wrapper (preferred for grouping)
- direct list of rules
- single rule object

## Service Mode (recommended)

`make quickstart` is the one-command path.

If you prefer manual steps:

1. Configure (generate files):

```sh
python3 configure.py
```

2. Install (this also runs `configure.py` so you don't need to run it separately):

```sh
make install
```

3. Enable + start:

```sh
make start
```

Manage:

```sh
make status
make logs
make restart
make stop
```

**Notes about linger (boot-start user services):**

User services normally start when you log in. To allow them to start at boot and keep running after logout:

```sh
sudo loginctl enable-linger <your-username>
loginctl show-user <your-username> | grep Linger
```

`configure.py` will optionally offer to enable linger for you.

## Manual Mode

Start `signal-cli` DBus daemon (session bus):

```sh
signal-cli -a +15551234567 daemon --dbus
```

Run the agent directly:

```sh
python3 signal-agent.py ./rules.yaml
```

Or run each in `screen` (dev/test):

```sh
screen -S signal-cli
signal-cli -a +15551234567 daemon --dbus
# Ctrl-A D to detach

screen -S signal-agent
python3 signal-agent.py ./rules.yaml
# Ctrl-A D to detach
```

## Sample Usage

Below are small sample rules (you can place them in `rules.d/` or in the shipped template `templates/rules/example-rules.yaml.in`).

### 1) Home directory listing

```yaml
- name: home_dir_list
  sender: "+15551234567"
  trigger: "home directory?"
  match: exact
  command: ["ls", "-lah", "/home/user"]
  reply_mode: full
```

Send `home directory?` → agent runs `ls -lah /home/user` and replies with the output.

---

### 2) Tail journal entries (regex + arg validation)

```yaml
- name: journal_tail
  sender: ["+15551234567"]
  trigger: "^tail journal (\\d+)$"
  match: regex
  command_template: ["journalctl", "-n", "{n}", "--no-pager"]
  args:
    n:
      type: int
      min: 1
      max: 200
  reply_mode: output
```

Send `tail journal 50` → agent runs `journalctl -n 50 --no-pager` and replies with the output only.

---

### 3) Disk usage (reply routed to admin)

```yaml
- name: disk_usage
  sender:
    - "+15551234567"
  trigger: "disk?"
  match: exact
  command: ["df", "-h"]
  reply_to: admin
  reply_mode: output
```

`reply_to: admin` uses the `globals.admin` setting in `rules.yaml` as the recipient.

## Reply Modes

Per-rule `reply_mode` options:

- `full` (default): `[rule] exit=0` + `$ command` + output  
- `output`: `[rule]` + output only  
- `bare`: output only

Use `reply_prefix` / `reply_suffix` in either globals or per-rule to add consistent header/footer to replies.

---

## Chunked Output

Large outputs can be split to avoid message size limits:

```yaml
split_reply: true
chunk_size: 1400
numbered_chunks: true
```

If output splits into multiple messages and `numbered_chunks: true`, each message will get a prefix like:

- `[rule message 1/2]`
- `[rule message 2/2]`

If the entire output fits in one message, **no** chunk prefix is added.

## Multiple Allowed Senders

`sender` may be a string or a list:

```yaml
sender: "+15551234567"
# or
sender:
  - "+15551234567"
  - "+15557654321"
```

An omitted or empty `sender` allows all senders (use carefully).

## Dry Run & Test Mode

- Global dry-run: `globals.dry_run: true` in `rules.yaml` or `--dry-run` CLI flag. Commands still execute but sends are suppressed.
- Per-rule dry-run: `dry_run: true` on the rule.
- Test mode (local simulation, no DBus):

```sh
python3 signal-agent.py ./rules.yaml --test --sender "+15551234567" --message "disk?"
```

`make test` runs the agent in test mode (overrides available via `TEST_SENDER` / `TEST_MESSAGE`).

## Uninstall / Clean (safe)

- `make uninstall` — stops + disables + removes installed **user** units (from `~/.config/systemd/user/`). **Does not** touch your `rules.d/` user rules.
- `make clean` — removes repo-generated artifacts only:
  - `rules.yaml`
  - `systemd/*.service` (rendered)
  - `rules.d/example-rules.yaml` (the shipped example we render)
  - **Does not** delete other files in `rules.d/` (your custom rules are preserved)

If you enabled linger and want to disable it:

```sh
sudo loginctl disable-linger <your-username>
loginctl show-user <your-username> | grep Linger
```

## Security Considerations

This agent executes host commands triggered by Signal messages. Treat it as a privileged automation surface:

- Restrict `sender` to trusted numbers (or lists)
- Prefer `exact` matching when possible
- Validate regex arguments (`args`) and set bounds
- Use rate limits (`cooldown_sec`, `max_runs_per_hour`)
- Redact sensitive output via `globals.redact_regex`
- Never commit secrets (tokens, API keys) to the repo — store them in protected files (e.g., `~/.config/signal-agent/ha_token`, `chmod 600`)
- Run the agent as a low-privilege user
- Consider auditing / logging and using `dry_run` before enabling powerful commands
